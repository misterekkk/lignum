One benchmark, run the same way on every machine: the same model files (500 boosting rounds with 63
leaves, or CatBoost's 64), seven data sets, batches from 1 to 1,000,000 rows, and a different row on
every call. Every engine is checked against the library's own `predict`: lignum equals it bit for
bit in all 140 of its runs (both machines, numpy and Arrow input); lleaves never does, and TL2cgen
does not for XGBoost.
How it is measured, and what it does not show, is under [Methodology](#methodology).

## Where lignum is not the fastest

- **Covertype, one row, on the M4**: lleaves takes 38 µs, lignum compiled 43 µs (the median; the p99
  is about equal). On the x86 server lignum is 2× faster on the same model.
- **The compiled mode on single rows**: its median matches the interpreter's, but its p99 is worse
  (x86: 23.7 vs 31.0 µs on California), and on Covertype (3,500 trees) the interpreter is clearly
  faster on x86 (91 vs 142 µs). One row runs each tree's code once, and a large model's code does not
  fit the instruction cache (32 KB on Zen 3). Use the interpreter for single rows, or let
  [`autotune`](../guides/compiled/#interpreter-or-compiled-autotune) choose.
- **Compiling large models**: 13 s (M4) and 22-27 s (x86) for the 3,500 trees of Covertype; the
  interpreter needs no compiler and loads every model on this page in under a second (0.7 s at most).
- **Single rows from Arrow**: exporting a pyarrow table costs time per column on every call, so a
  numpy row is faster (x86, Covertype with 54 columns: 91 µs from numpy, 141 µs from Arrow).
- **CatBoost, numeric models, all threads on x86**: CatBoost evaluates float features with
  hand-written SSE code, and lignum's lead shrinks to 5-11% on California and the synthetic numeric
  set (Covertype, with 7 classes, stays 4.3×).

## Methodology

**Models.** 500 boosting rounds, learning rate 0.1, seed 7, trained once on 80% of each data set
and copied to every machine: every report lists each model file's SHA-256.

| Library | Trees | Parameters |
|---|---|---|
| LightGBM 4.7 | leaf-wise, up to 63 leaves | `num_leaves=63`, `max_depth=-1` |
| XGBoost 3.4 | leaf-wise, up to 63 leaves | `tree_method="hist"`, `grow_policy="lossguide"`, `max_leaves=63`, `max_depth=0` |
| CatBoost 1.2.10 | symmetric, 64 leaves | `depth=6` (the default; lignum reads symmetric trees only) |

XGBoost's `lossguide` grows trees best-first, as LightGBM does; it is the pairing LightGBM's own
comparison with XGBoost uses. CatBoost's symmetric trees are the closest match, not an identical one.
Leaf-wise trees with 63 leaves are not all as deep: an average row passes 4.4-9.8 comparisons per
tree in the LightGBM models and 3.7-7.4 in the XGBoost ones (listed per model in the reports).
Multiclass models (Covertype, 7 classes) have 500 rounds, so 3,500 trees for LightGBM and XGBoost.

**Data sets.** California housing (20,640 rows, 8 numeric features), Covertype (581,012 rows, 54
features, 7 classes), Adult (32,561 rows, 8 categorical features), Bank marketing (45,211 rows, 9
categorical), Diabetes 130-US (101,766 hospital stays, 39 of
47 features categorical, among them ICD diagnosis codes with hundreds of values), `synthetic` (20 numeric features, 5% NaN) and `synthetic-cat` (5
categorical columns of 10 to 5,000 Zipf-skewed values and 15 numeric ones). Small batches are drawn from
the whole data set; batches larger than it repeat its rows.

**Small batches (1, 10, 100 rows)**: up to 100,000 calls after a warm-up, each on the next of 1,000
different batches, so that neither the branch predictor nor the caches learn one row. The reports
give the median, p99 and p99.9 of the calls. **Large batches (10,000, 100,000 and 1,000,000 rows)**:
the median and best of at least 3 repeats on different windows of rows. Each on one thread and on
all threads. This page shows 1 row and 1,000,000 rows; the reports have every size.

**Exactness.** Every engine predicts the held-out rows (up to 100,000) and as many training rows,
compared with the library's `predict` bit for bit (raw scores for regression, probabilities for classification).

**Engines.** lignum 0.4.0 at commit `40529d9` (the compiled engine's preparation times on the M4 from
`41dcee1`, which runs the C compiler in parallel on macOS); lleaves 1.3.0 (`compile()`, its default
settings); TL2cgen 1.0.0 with Treelite 4.7 / 4.8 (`export_lib`, `-O3`, `parallel_comp` = number of
cores; gcc 13.3 on x86, Apple clang 17 on the M4). On x86 TL2cgen is much slower than on the M4, also
next to the other engines: its generated code walks every tree for each row and is large (47 MB of C
for Covertype), which a 32 KB instruction cache and 512 KB L2 hold far less of than the M4's; gcc may
also optimise such huge functions less well than clang. On all threads lleaves starts its threads on
every call, so its single-row times there are not shown; on one thread they are its best.

**Machines.** Hetzner CCX33: AMD EPYC-Milan, 8 dedicated vCPU (4 cores with SMT), 32 GB, Ubuntu 24.04,
Python 3.12 (`benchmarks/cloud.sh`). MacBook Pro with Apple M4: 4 performance and 6 efficiency
cores, 16 GB, macOS 26, on power with other heavy applications closed. "All threads" means 8 and 10;
the M4's efficiency cores take part. An ARM server (Hetzner CAX, Ampere Altra) follows when one is
available.

## Reproduce

```bash
make venv bench-deps py-build
.venv/bin/python benchmarks/suite.py                  # trains the models once, then measures
.venv/bin/python benchmarks/suite.py --quick --datasets california   # a smoke run
```

`benchmarks/cloud.sh` runs the same on a fresh Ubuntu server from the models trained on your
machine. The reports behind this page, with every batch size, p99.9 and the SHA-256 of every model,
are in [`benchmarks/results/`](https://github.com/misterekkk/lignum/tree/main/benchmarks/results).
